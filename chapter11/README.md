# C++ 文件 I/O 深度指南

## 一、核心二元论：两个维度的解耦

理解文件操作的关键在于拆分"你调用的函数"与"操作系统的行为"。

### 维度 A：数据的格式化方式（Formatted vs. Unformatted）

决定内存数据如何变成字节流：

| 方式 | 操作符/函数 | 本质 | 目标 |
|------|------------|------|------|
| **格式化 I/O** | `<<`, `>>`, `printf`, `scanf` | 数据转换：将数值（如 `int 123`）转为字符 `'1','2','3'` | 生成人类可读的文本 |
| **非格式化 I/O** | `read()`, `write()` | 数据拷贝：直接将内存原始位（Raw Bits）搬运到流中 | 生成机器高效处理的二进制数据 |

### 维度 B：流的传输模式（Text vs. Binary Mode）

决定数据在"流向硬盘"过程中，系统是否进行二次加工：

| 模式 | 开启方式 | 行为 | 风险 |
|------|---------|------|------|
| **文本模式**（默认）| 默认 | 换行符翻译：Windows 下 `\n`(10) -> `\r\n`(13,10) | 非格式化写入时若某字节值为 10，系统会多插入一个字节，**导致数据损坏** |
| **二进制模式** | `ios_base::binary` | 原样传输，OS 承诺不触碰任何字节 | 无 |

> **规则**：处理图片、结构体、int 数组等非格式化数据时，**必须**开启二进制模式。

---

## 二、场景组合矩阵

| 读写方法 | 打开模式 | 结果与典型应用 |
|---------|---------|--------------|
| 格式化 (`<<`) | 文本模式 | 标准文本文件。存储 `.txt`/`.csv`，跨平台换行符自动适配 |
| 非格式化 (`write`) | 二进制模式 | 纯正二进制文件。存储图像、模型数据或内存镜像，速度最快，体积最小 |
| 非格式化 (`write`) | 文本模式 | 危险区。换行符翻译极大概率导致 Windows 上数据损坏 |
| 格式化 (`<<`) | 二进制模式 | 强制风格文本。例如在 Windows 上强制生成 Linux 风格（只有 `\n`）的文本文件 |

## 三、进入二进制世界的三个"幽灵"

使用非格式化 I/O 时，需时刻警惕以下底层差异：

### 1. 字节序（Endianness）
同一个 `int`，在 Intel CPU（**小端**）和网络协议（**大端**）中的字节顺序是反的。跨平台传输二进制文件需手动进行字节翻转（`htonl`/`ntohl` 等）。

### 2. 结构体对齐（Padding）
编译器为提升 CPU 访问效率，会在结构体成员间填充空白字节。直接 `write` 整个结构体可能导致文件包含"随机垃圾"字节，跨平台/跨编译器时结构布局可能不同。

### 3. 指针失效（Pointer Validity）
内存地址在程序重启后会改变。**绝对不能**直接写入包含指针的结构体，必须进行**序列化（Serialization）**处理，将指针解引用为值后再写入。

## 四、C++ 底层 I/O 内存模型与寻址机制

### 4.1 数据流转的四层宏观架构

数据读写并非直接落盘，而是经历严格的四级接力：

```
应用内存数据
    |
C++ 流缓冲区 (std::streambuf)  <- 用户态 ~8KB 内存池，减少系统调用
    |
OS 内核缓冲区 (Page Cache)     <- 操作系统文件系统缓存
    |
外部物理 I/O                   <- 硬盘、终端、网络等
```

### 4.2 核心游标与相对寻址公式

`tellg()` / `tellp()` 并不直接调用系统 API，而是通过内存指针进行极速数学推算：

**输入区（Get Area）**

| 指针 | 含义 |
|-----|------|
| `eback()` | 缓冲区可读起点（put-back 区末尾） |
| `gptr()` | 当前读取游标 |
| `egptr()` | 缓冲区可读末尾 |

```
tellg() 逻辑位置 = 缓冲区外部物理基址 + (gptr() - eback())
```

**输出区（Put Area）**

| 指针 | 含义 |
|-----|------|
| `pbase()` | 缓冲区写入起点 |
| `pptr()` | 当前写入游标 |
| `epptr()` | 缓冲区写入末尾 |

```
tellp() 逻辑位置 = 缓冲区外部物理基址 + (pptr() - pbase())
```

### 4.3 寻址操作（Seek）的底层执行逻辑

以目标位置 `target_pos` 为例：

**情景 A：缓存命中（Buffer Hit）**
- **条件**：`target_pos` 落在当前缓冲区覆盖的物理范围内
- **动作**：极速微操，不产生任何真正的 I/O 操作
- **执行**：
  - 读取：`gptr = eback() + (target_pos - 缓冲物理基址)`
  - 写入：`pptr = pbase() + (target_pos - 缓冲物理基址)`

**情景 B：缓存未命中（Buffer Miss）**
- **条件**：`target_pos` 超出当前缓冲区范围
- **动作**：触发系统调用
- **执行**：
  1. 对写操作（`seekp`）：先将 `pbase()` 到 `pptr()` 的脏数据 `flush/sync` 到 OS 内核
  2. 废弃当前 C++ 流缓冲区中的所有内容
  3. 调用底层 OS API（如 `lseek`）将物理指针移动到 `target_pos`
  4. 重新确立"缓冲区外部物理基址"，重置 C++ 游标

### 4.4 `ios_base::cur` 的基准

| 操作 | 相对零点 |
|-----|---------|
| `seekg(off, cur)` | 当前 `gptr` 逻辑位置 |
| `seekp(off, cur)` | 当前 `pptr` 逻辑位置 |

## 五、致命禁忌与避坑指南

### 禁忌一：文本模式下使用绝对定位
Windows 文本模式存在 `\r\n` <-> `\n` 的自动转换，导致物理字节数与逻辑字符数不一致，打破寻址推算公式，造成 `tell`/`seek` 定位错乱。

> **规则：凡使用 `seekg`/`seekp` + `tellg`/`tellp` 进行绝对定位，必须用二进制模式打开文件。**

### 禁忌二：混淆 `app` 与 `ate`

| 标志 | 全称 | 行为 |
|-----|------|------|
| `ios_base::app` | Append | **强制焊死**：无论怎么 `seekp`，每次写入前系统都会强行将游标拽回文件末尾 |
| `ios_base::ate` | At End | **自由移动**：初始游标在末尾，但允许通过 `seekp` 回到任意位置进行覆盖修改 |

## 六、进阶细节

### 6.1 `seekp` 移动后的"内存空洞"与"脏数据"

- **向后跳**（`offset < 0`）：`pptr` 回退，后续写入将覆盖缓冲区中的旧数据（改写历史）
- **向前跳**（`offset > 0`）：
  - **缓冲区内**：`pptr` 越过一段内存，该段可能包含上次操作残留的脏数据
  - **跨缓冲区（文件空洞）**：若 `seekp` 跳到文件末尾之后，OS 在磁盘上创建"稀疏空洞"（Sparse File），读取时通常返回 `\0`（Null bytes）

### 6.2 状态切换的"金科玉律"

在同一个 `fstream`（读写双向流）中，**切换读写动作前必须进行一次 `seek` 或 `sync`**。

**原因**：`gptr` 和 `pptr` 在某些系统底层共享物理文件指针，不进行 `seek` 可能导致读到尚未落盘的缓冲数据，造成逻辑混乱。

```cpp
// 即使不移动位置，也建议"原地踏步"以强制同步缓冲区状态
f.seekp(f.tellp());
```

### 6.3 类型感应与跨平台

- `pos_type` / `off_type`：流内部嵌套类型别名，具备"类型感应"
  - `char` 流：单位为 1 字节
  - `wchar_t` 流：单位可能为 2 或 4 字节
- 这些类型在**编译期**根据模板参数（`Traits`）确定，保证操作的原子性与类型安全

## 七、常用操作速查表（Cheat Sheet）

| 需求 | 代码 |
|-----|------|
| 获取当前读取位置 | `pos_type p = ifs.tellg();` |
| 跳到文件起始第 N 字节 | `ifs.seekg(N, ios::beg);` |
| 跳到文件末尾 | `ifs.seekg(0, ios::end);` |
| 在当前位置后退 5 字节 | `ifs.seekg(-5, ios::cur);` |
| 获取文件总大小 | `ifs.seekg(0, ios::end); size_t sz = ifs.tellg();` |
| 修改特定位置数据 | `ofs.seekp(pos); ofs.write(...);` |
| 读写切换（原地同步） | `f.seekp(f.tellp());` |

## 八、练习题

### 练习一：就地修改二进制文件中的字段

**场景**：你维护一个简单的"学生成绩库"，数据以固定格式存储在二进制文件中，需要能精准定位并修改某个学生的成绩，而**不重写整个文件**。

**数据结构**：
```cpp
struct Student {
    char  name[20];  // 固定长度姓名
    int   id;        // 学号
    float score;     // 成绩
};
```

**要求实现以下三个函数**：

```cpp
// 1. 初始化：将若干个 Student 写入二进制文件 students.dat
void createDatabase(const std::string& filename, const std::vector<Student>& students);

// 2. 读取：按 id 查找并打印某个学生的信息
void findStudent(const std::string& filename, int id);

// 3. 修改：按 id 找到该学生，就地修改其 score，不得重写其他记录
void updateScore(const std::string& filename, int id, float newScore);
```

**验证方式**：
1. 写入 3 个学生
2. 修改第 2 个学生的成绩
3. 重新读取全部学生，确认只有第 2 个发生变化
4. 用 `xxd students.dat` 确认文件大小始终不变

**核心考点**：`seekp` 定位到 `id * sizeof(Student) + offsetof(Student, score)` 的精确位置后写入。

### 练习二：结构体序列化与反序列化

**分两个阶段完成。**

#### 阶段 A：踩坑实验

定义如下结构体（故意设计成有 Padding 的）：

```cpp
struct Packet {
    char   type;    // 1 字节
    // 此处有几个字节的 padding？你来猜，再用程序验证
    int    length;  // 4 字节
    char   flag;    // 1 字节
    // 此处又有几个字节的 padding？
    double value;   // 8 字节
};
```

**要求**：
1. 用 `sizeof` 和 `offsetof` 打印出每个字段的偏移量和结构体总大小，画出内存布局图
2. 直接用 `write` 将该结构体写入文件，再用 `read` 读回，验证数据是否正确
3. 用 `#pragma pack(1)` 模拟不同对齐后读取同一个文件，看数据是否错乱

#### 阶段 B：实现真正的序列化

**不允许直接 `write` 整个结构体**，改为逐字段写入：

```cpp
// 手动序列化：按字段逐个写，消除 padding 影响
void serialize(std::ostream& out, const Packet& p);

// 手动反序列化：按字段逐个读
Packet deserialize(std::istream& in);
```

**验证**：
1. 序列化写入文件，检查文件大小是否等于 `1+4+1+8 = 14` 字节（而不是 `sizeof(Packet)`）
2. 反序列化读回，所有字段值正确

**Endianness 扩展（选做）**：
- 在 `serialize` 中，将 `int` 和 `double` 统一转为大端字节序写入（模拟网络协议）
- 在 `deserialize` 中做对应的转换
- 提示：用 `uint32_t` 配合位移操作手写字节翻转，不要用 `htonl`

### 练习三：文本模式 vs 二进制模式写入对比

**数据**：一个包含换行符陷阱值的整数数组：
```cpp
std::vector<int> data = {10, 0x0A, 127, 0x0D0A, 255, 13, 10};

| 文件名 | 写法 | 打开模式 |

**对每个文件，程序需要输出**：

...
```

**最终要得出的结论**：
1. 哪种组合写入和读回的数据**完全一致**？
2. `raw_text.dat` 在 Windows 上文件大小为何与预期不符？
3. `fmt_bin.dat` 与 `fmt_text.dat` 在 Linux 上大小是否相同？在 Windows 上呢？

## 📝 C++ I/O 流格式化深度总结 (Chapter 11 补充)

### 1. 底层状态管理：setf 与 unsetf
C++ 流通过内部标志位（flags）控制输出行为。`setf` 是“拨动开关”，`unsetf` 是“关闭开关”。

| 函数原型 | 逻辑描述 | 适用场景 |
| :--- | :--- | :--- |
| `setf(flag)` | **追加开启**：不影响同组其他标志 | 独立开关（如 `showpos`, `uppercase`） |
| `setf(flag, mask)` | **安全切换**：先清除 `mask` 组，再开启 `flag` | 互斥组切换（如进制、浮点模式、对齐） |
| `unsetf(mask)` | **彻底关闭** | 恢复默认状态或关闭特定功能 |

#### 核心互斥组 (Fields)
- `ios::basefield`: `dec`, `hex`, `oct`
- `ios::floatfield`: `fixed`, `scientific`
- `ios::adjustfield`: `left`, `right`, `internal`

---

### 2. 浮点数格式化：模式与精度的联动
`setprecision(n)` 的含义取决于当前的 `floatfield` 状态。

| 浮点模式 | 开启方式 | `setprecision(n)` 含义 | 自动去尾零 |
| :--- | :--- | :--- | :--- |
| **Default** | `defaultfloat` | **总有效数字**为 $n$ 位 | 是 |
| **Fixed** | `fixed` | **小数点后**固定 $n$ 位 | 否 (补零) |
| **Scientific** | `scientific` | **小数点后**固定 $n$ 位 | 否 (补零) |

> **defaultfloat 切换逻辑**：
> 假设 $X = d.ddd \times 10^e$。若 $e < -4$ 或 $e \geq$ 精度 $P$，则自动切为科学计数法，否则使用定点小数。

---

### 3. 流操纵符 (Manipulators) 的运行本质
`std::cout << std::hex;` 并非简单的变量输入，而是一个**函数回调**过程。

1. **函数定义**：`std::hex` 是一个接受 `ostream&` 并返回 `ostream&` 的全局函数。
2. **重载匹配**：`ostream` 重载了 `operator<<` 以接受这种函数指针。
3. **执行回调**：`cout` 在内部调用 `hex(cout)`。
4. **底层操作**：`hex` 函数内部执行 `str.setf(ios::hex, ios::basefield)`。

---

### 4. 常用工程代码片段
```cpp
// 1. 强制保留两位小数 (财务格式)
cout << fixed << setprecision(2) << 123.4; // 123.40

// 2. 恢复默认浮点状态 (C++11)
cout << defaultfloat; 

// 3. 打印大写十六进制并带前缀
cout << showbase << uppercase << hex << 255; // 0XFF


💡 C++ I/O 架构设计：三大核心直觉问题
当你面对一个新的 I/O 处理任务时，不要急着写代码，先在心里问自己以下三个问题。它们将决定你掏出的是“轻量级流水线”，还是“高层结构化容器”。

❓ 问题 1：当前字符的意义，需要结合上下文（后续字符）来决定吗？
❌ 不需要

场景：大小写反转、删除元音、大文件加密。

决策：流式过滤 (std::cin.get() / std::cout.put())。

原因：字符之间相互独立，来一个处理一个，效率最高。

✅ 需要

场景：前缀 0x 代表十六进制、[ 开头代表日志级别、( 代表坐标起点。

决策：结构化解析 (std::cin >> std::string 或 std::getline)。

原因：必须拿到一个完整的“语义块（Token）”才能进行业务判断。

❓ 问题 2：如果发生解析错误，我需要原样打印出用户输入的那一整块错误内容吗？
❌ 不需要

场景：错了直接退出、悄悄忽略坏数据、或者只需要全局报错。

决策：可以考虑流式处理。

✅ 需要

场景：友好的命令行交互、编译器报错提示（如：“错误：'0x4G' 不是合法的十六进制数”）。

决策：必须先当成 Token 存进 std::string。

原因：输入流（Stream）是单向的，一旦用 get() 吃掉就再也吐不出来了。只有存进字符串，才能在报错时原样输出。

❓ 问题 3：输入的数据规模会无限长，或者单行长度极其恐怖吗？
❌ 不会

场景：配置文件解析、用户命令行零星输入、固定格式的短小日志。

决策：放心使用 std::string 或容器存储。

✅ 有可能

场景：处理数 GB 的大型基因序列、巨大的压缩文件、无换行的网络流。

决策：强制要求使用流式过滤，绝对不能用 string 一把抓。

原因：用 getline 或 string 存储超长单行会触发大内存分配，轻则变慢，重则导致内存溢出（OOM）崩溃。
